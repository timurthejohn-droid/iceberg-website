# Бэкенд + админка iceberg.spb.ru — архитектура и заливка на сервер

> Как это устроено и как поднять на sprinthost, когда придёт доступ.
> Требования к хостингу — [SERVER-REQUIREMENTS.md](SERVER-REQUIREMENTS.md). Защита — [SECURITY.md](SECURITY.md).

---

## 1. Идея в двух абзацах

Сайт остаётся статикой. Мы **не переписываем страницы**: готовый HTML каждой управляемой страницы
кладём как «эталон» (baseline), а тонкий PHP-слой **накладывает** поверх него правки из админки —
SEO-теги в `<head>`, заголовок H1, отмеченные маркерами куски текста, фото, оффер посадочной.
Всё, что не тронуто в админке, отдаётся **байт-в-байт как раньше**, поэтому бережно сохранённые
SEO-сигналы (title/canonical/редиректы из seo.md) не страдают. Это проверяется автоматически.

Результат каждой страницы **кэшируется** в файл: PHP отрабатывает только на первый запрос после
сохранения правки, дальше страница отдаётся со скоростью статики. Админка — отдельное приложение
под `/admin/`, вход по паролю + 2FA, с двойным заслоном на уровне сервера.

> ⚠️ **Источник страниц — `04-site-iceberg/dist/`** (сборка подрядчика, принята 4 сент 2026).
> Python-скрипты `build_v3.py` / `build_pages.py` генерируют НАШУ версию от 19 августа и при запуске
> затрут dist. Для этого сайта они больше не используются — правится готовый HTML в `dist/`.

## 2. Карта компонентов

```
Браузер ──▶ Apache (.htaccess — ОДИН объединённый файл)
              │  • SEO-редиректы и 410 на остатки WordPress — срабатывают первыми
              │  • реальный файл (hero-assets, _wp, og-cover.jpg, send.php, uploads) → отдаёт сам
              │  • /admin/*  → public/admin/index.php  (админка)
              │  • всё остальное → public/index.php    (фронт-контроллер сайта)
              ▼
        public/index.php
              │  1. адрес есть в реестре страниц? → Overlay(эталон + правки из БД) → кэш → отдать
              │  2. иначе                          → 404 (страница 404.html)
              ▼
        app/  (ядро: БД, наложение, кэш, медиа, заявки, безопасность)
              ▼
        data/content.db  (SQLite: контент, заявки, пользователи, журнал)
```

Ключевые модули (`app/lib/`):

| Файл | Отвечает за |
|---|---|
| `Database.php` | подключение к SQLite (PDO) + создание схемы (миграции) |
| `Auth.php` | вход, argon2id-пароли, сессии, блокировка перебора |
| `Totp.php` | двухфакторный код (Google/Яндекс Authenticator и совместимые) |
| `RateLimiter.php` | лимит попыток входа, нарастающая задержка |
| `Csrf.php` | защита форм от подделки запросов |
| `Security.php` | security-заголовки, HTTPS, укрепление сессии |
| `Audit.php` | журнал: кто, когда и что менял |
| `PageRegistry.php` | **список управляемых страниц и всех редактируемых полей** |
| `Content.php` | чтение/запись контента и глобальных настроек, история правок |
| `Overlay.php` | **наложение правок на эталонный HTML** |
| `Cache.php` | полностраничный кэш и его сброс при сохранении |
| `Media.php` | загрузка фото с проверками и пересжатием |
| `Leads.php` | заявки: разбор журнала форм, статусы, поиск, выгрузка CSV |

Проверки в `bin/`: `check_env.php` (подходит ли хостинг) · `check_deploy.php` (правильно ли всё разложено) ·
`check_seo.php` (не разъехались ли поисковые сигналы, в т.ч. сверка с живым сайтом).

## 3. Что под управлением

**11 страниц:** главная · ткани-оптом · контакты · вакансии · посадочная производства
(флагман `/shveinoe-proizvodstvo/`) · 4 подстраницы производства · политика конфиденциальности ·
соглашение о cookie.

**Не управляются намеренно** — отдаются как статические снимки, чтобы не рисковать SEO:
`/emdi/`, `/technicheskie-tkani/`, прайс. Это 1:1 копии живых WP-страниц.

Что редактируется:

| Где | Что |
|---|---|
| Любая страница | Title, Description, OG-заголовок/описание/картинка, H1; в «дополнительно» — canonical и robots |
| Главная | первый экран, 4 карточки компаний (текст + фото), 4 блока «Для кого» (текст + фото), блок с яхтой, «О группе» с тремя фактами, «Группа в цифрах», блок контактов |
| Внутренние | весь текст страницы одним блоком + заголовок и подпись над формой заявки |
| Посадочная | оффер первого экрана (он задаётся скриптом, а не вёрсткой) и заголовок финального блока |
| Юридические | текст политики и соглашения о cookie — сейчас там заглушки |
| Глобально | телефон, e-mail, картинка-превью по умолчанию |
| Заявки | всё, что пришло с форм: статусы, заметки, поиск, выгрузка в CSV |

**Форма заявки не редактируется намеренно.** В ней согласие на обработку данных (152-ФЗ),
ловушка для ботов и адрес обработчика — случайная правка сломала бы приём заявок или нарушила закон.

Точки правки размечены в HTML комментариями `<!--cms:КЛЮЧ-->…<!--/cms:КЛЮЧ-->`.
Ставит их `tools/cms_markers.py` (идемпотентно, с проверкой каждого якоря).

## 4. Заливка на sprinthost (пошагово)

**Шаг 0. Проверить, что разметка на месте**
```bash
python3 tools/cms_markers.py --check     # должно быть «уже размечена» по всем страницам
```

**Шаг 1. Разложить файлы на сервере**
```
~/app/            ←  backend/app/  целиком   (ВНЕ веб-корня)
~/app/baseline/   ←  создастся на шаге 3
~/data/           ←  пустой, права на запись (база, кэш, бэкапы)   (ВНЕ веб-корня)
~/public_html/
     ├── (содержимое 04-site-iceberg/dist/ — весь сайт, включая send.php, lib/, mail-config.php)
     ├── index.php     ←  backend/public/index.php
     ├── .htaccess     ←  backend/public/.htaccess     ⚠️ ПОВЕРХ того, что пришёл из dist/
     ├── admin/        ←  backend/public/admin/
     └── uploads/      ←  backend/public/uploads/ (там .htaccess с запретом исполнения)
```

> ⚠️ **Порядок важен.** Сначала `dist/`, потом файлы из `backend/public/`. В `dist/` свой `.htaccess`
> (только SEO-редиректы), в бэкенде — **объединённый** (редиректы + роутинг + защита). Нужен второй.
> Если перепутать: либо перестанут работать редиректы, либо админка и страницы отдадут 404.
> Проверка на шаге 5 это ловит.

**Шаг 2. Прописать пути и секрет** — скопировать `app/config.example.php` → `app/config.php`:
```php
'DATA_DIR'     => '/home/ЛОГИН/data',
'BASELINE_DIR' => '/home/ЛОГИН/app/baseline',
'PUBLIC_DIR'   => '/home/ЛОГИН/public_html',
'BASE_URL'     => 'https://iceberg.spb.ru',
'APP_SECRET'   => '…',        // openssl rand -hex 32
'LEADS_LOG'    => '',         // пусто = public_html/leads.log, куда пишет send.php
```

**Шаг 3. Поднять базу, эталоны и админа**
```bash
php bin/check_env.php          # подходит ли хостинг (потом удалить файл)
php bin/install_layout.php     # переносит 11 страниц из public_html в baseline
php bin/create_admin.php       # логин и пароль администратора
php bin/seed.php               # заводит страницы, показывает распознанные title
```

**Шаг 4. Первый вход.** Открыть `/admin/`, войти, привязать 2FA (приложение-аутентификатор:
Google Authenticator, Яндекс.Ключ, Authy, 1Password).

**Шаг 5. Предполётная проверка**
```bash
php bin/check_deploy.php
```
Показывает списком: разложено ли всё, тот ли `.htaccess`, все ли страницы с метками правки,
не осталось ли дублей страниц в веб-корне, заполнены ли настройки почты, не остались ли
юридические страницы заглушками. Строки `!!!!` — то, что блокирует запуск.

**Шаг 5а. Сверка склейки** (переезд с сохранением позиций):
```bash
php bin/check_seo.php --live https://iceberg.spb.ru   # ДО переключения — и сразу ПОСЛЕ
```
`title` и `canonical` обязаны совпадать 1-в-1. Подробности — в корневом `03-seo/README.md` §3.2.

**Шаг 6. Убрать временное.** Удалить `bin/check_env.php` и `bin/check_deploy.php` с сервера.
Убедиться, что `~/app/` и `~/data/` из браузера дают 403.

**Шаг 7. Включить второй заслон на админку** (по желанию, см. `public/admin/.htaccess`):
```bash
htpasswd -c /home/ЛОГИН/.htpasswd-admin имя_для_входа
```
и раскомментировать 4 строки `Auth*` в `admin/.htaccess`. Сначала проверить путь — при неверном
пути `/admin` отдаст 500.

## 5. Как уживаются правки разработчика и правки маркетолога

- **Дизайн и структуру** правит разработчик — прямо в `dist/`. После этого:
  `python3 tools/cms_markers.py` (вернуть метки) → `php bin/install_layout.php` (обновить эталоны).
  Правки из админки лежат отдельно в базе и **накладываются на новый эталон автоматически** —
  если ключи полей и метки не поменялись. Что не легло, админка честно скажет при сохранении.
- **Текст, SEO, фото, заявки** день в день ведёт маркетолог в админке — без разработчика и без выкладки.

## 6. Резервные копии и откат

- `bin/backup.php` — архив `content.db` + `uploads/` в `data/backups/` (можно в cron).
- Каждое изменение поля сохраняет прежнее значение в историю (`field_history`).
- Очистить поле в админке = вернуть **эталонное** значение из вёрстки. Это и есть быстрый откат.
- Полный откат сайта на WordPress — по бэкапу из RUNBOOK.md (03-seo/README.md), это отдельный слой.

## 7. Что проверено локально (сент 2026)

Стенд поднимался на статической сборке PHP 8.3 (локально PHP на машине не установлен):

- все 11 страниц без правок отдаются **байт-в-байт** как эталон;
- «сохранить, ничего не изменив» не создаёт правок ни на одной странице;
- правки текста, SEO, фото, оффера посадочной доходят до страницы, вёрстка и шейдер целы;
- форма заявки, согласие 152-ФЗ и ловушка для ботов после правки текста остаются на месте;
- смена телефона и почты не задевает контакты отдела кадров на странице вакансий;
- заявки читаются из журнала форм, не задваиваются, выгружаются в CSV;
- при недоступной базе страницы отдаются **эталоном байт-в-байт (200)**, а не 500;
  при пропаже эталона — **503 + Retry-After**, чтобы адрес не выпал из индекса;
- объединённый `.htaccess` проверен на настоящем Apache: страницы уходят на фронт-контроллер,
  `/admin/` и `/send.php` — нет, редиректы и 410 работают, `/index.php` не зацикливается.
