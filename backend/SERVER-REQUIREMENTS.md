# Требования к серверу — админка и бэкенд iceberg.spb.ru

> Что должно быть на хостинге, чтобы «залить папку — и всё работает».
> Стек выбран под sprinthost (обычный shared-хостинг на Apache): **PHP + SQLite**, без внешних сервисов.
> Последнее обновление: 19 августа 2026.

---

## 1. Минимальные требования (обязательно)

| Компонент | Требование | Зачем |
|---|---|---|
| **PHP** | версия **8.1+** (лучше 8.2/8.3) | argon2id-хеши паролей, современный синтаксис |
| **Веб-сервер** | Apache 2.4 с `mod_rewrite` и `mod_headers` | фронт-контроллер, редиректы, security-заголовки |
| **`.htaccess`** | разрешён (`AllowOverride All`) | вся логика роутинга/защиты в `.htaccess` |
| **База данных** | **SQLite 3** через `PDO` (расширения `pdo_sqlite` + `sqlite3`) | контент, пользователи, журнал — один файл, без сервера БД |
| **HTTPS** | сертификат (Let's Encrypt на sprinthost — бесплатно) | без TLS 2FA и cookie-защита бессмысленны |
| **Запись на диск** | папка `data/` доступна на запись PHP (0700/0750) | база, загрузки фото, кэш, бэкапы |
| **Память PHP** | `memory_limit ≥ 128M` | наложение контента на большие HTML главной |

### PHP-расширения (проверить `php -m`)
- `pdo`, `pdo_sqlite`, `sqlite3` — база **(критично)**
- `mbstring` — корректная работа с кириллицей
- `openssl` — генерация секретов/2FA, `random_bytes`
- `gd` **или** `imagick` — проверка и пересжатие загружаемых фото (обработка EXIF/размеров). Без них загрузка работает, но без пересжатия — менее безопасно; расширение желательно.
- `fileinfo` — определение реального MIME загружаемых файлов **(критично для защиты)**

> На sprinthost всё перечисленное входит в стандартный тариф. Отдельно докупать ничего не нужно.

## 2. Composer / внешние библиотеки — НЕ нужны

Весь код — **чистый PHP без зависимостей** (никакого Composer, npm, фреймворков).
2FA (TOTP), хеши, CSRF, загрузка файлов — реализованы вручную. Это осознанное решение:
меньше поверхности атаки, ничего не «протухнет», переносится копированием папки.

---

## 3. Структура на сервере (важно для безопасности)

Идеально — вынести код и данные **выше** веб-корня, чтобы из браузера были доступны только `public/`:

```
/home/иван/                     ← домашняя папка на хостинге
├── app/                        ← код приложения (НЕ доступен из веба)
├── data/                       ← база, загрузки, кэш, бэкапы (НЕ доступен из веба)
│   ├── content.db
│   ├── uploads/
│   ├── cache/
│   └── backups/
└── public_html/                ← ВЕБ-КОРЕНЬ (document root сайта)
    ├── index.php               ← фронт-контроллер
    ├── .htaccess
    ├── admin/                  ← вход в админку
    ├── hero-assets/ _wp/ ...    ← статика сайта
    └── og-cover.jpg ...
```

**Если хостинг не даёт вынести папки выше `public_html`** (частый случай на shared) — кладём
`app/` и `data/` внутрь `public_html/`, но их закрывают `.htaccess`-правила `Require all denied`
(идут в комплекте). Прямой доступ к базе и коду из браузера в обоих случаях заблокирован.
На sprinthost домашняя папка выше `public_html` доступна — используем первый, более строгий вариант.

## 4. Настройки веб-сервера, которые желательно попросить у хостера

Всё это либо уже так по умолчанию, либо ставится галочкой в панели sprinthost:

- **HTTPS + принудительный редирект** http→https (у нас есть правило в `.htaccess`, но лучше и на уровне панели).
- **PHP 8.1+** выбран для домена (в панели «версия PHP»).
- **`AllowOverride All`** для домена (чтобы `.htaccess` работал; на shared обычно включено).
- Директория `data/` — **права на запись** пользователю PHP.
- Желательно: **автобэкап** хостинга (у sprinthost есть) — как дополнительный слой к нашему `bin/backup.php`.

## 5. Ресурсы (оценка нагрузки)

Сайт корпоративный, трафик небольшой, весь тяжёлый контент (hero-кадры) — статика, отдаётся Apache напрямую.
Бэкенд включается только на HTML управляемых страниц, а те **кэшируются** (полностраничный кэш) — PHP
реально работает лишь на первый запрос после правки. Поэтому:

- **CPU/RAM:** хватает самого младшего тарифа shared-хостинга.
- **Диск:** код ~1–2 МБ + база (десятки КБ, растёт медленно) + загрузки фото (сколько зальёте) + hero-ассеты (~20 МБ, уже есть).
- **Трафик:** без изменений относительно текущего статического сайта.

## 6. Почта (для форм заявок) — опционально на этом этапе

Формы «Имя + Телефон» сейчас — заглушка + событие `lead_submit` в `dataLayer` (как в текущем сайте).
Когда подключим приём заявок, понадобится один из вариантов (не блокирует запуск админки):

- `mail()` / sendmail на хостинге (простейше), **или**
- SMTP клиента, **или**
- прямая интеграция с CRM клиента по API/вебхуку.

Выбор — отдельная задача (в CLAUDE.md/seo.md помечено «Формы → CRM»).

## 7. Чек-лист «спросить у клиента / хостера перед заливкой»

- [ ] Версия PHP на домене — **8.1+**?
- [ ] Есть `pdo_sqlite`, `fileinfo`, `mbstring`, `openssl`, `gd`/`imagick`? (скрипт-проверка — `bin/check_env.php`)
- [ ] HTTPS включён, http→https редирект работает?
- [ ] `.htaccess` (`AllowOverride All`) действует на домене?
- [ ] Можно вынести `app/` и `data/` выше `public_html`? (если нет — кладём внутрь, защита в комплекте)
- [ ] Доступ (FTP/SSH) для заливки — уже в процессе получения (см. seo.md, NEXT STEPS).

> Проверку окружения одной командой делает `bin/check_env.php` (кладём на сервер, открываем в браузере под паролем, читаем отчёт, удаляем).
